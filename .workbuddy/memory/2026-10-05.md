# 2026-10-05 · 市场日历

## 「利润断层」层内改为「利润断层 / 日历」双页卡

用户需求原话：**「进入『利润断层』界面后，移除单独用于返回投资日历的按钮，改为在该界面内提供两个可独立切换的页卡：
一个为『利润断层』，一个为『日历』，用户可以在两者之间自由切换。」**

### 关键判断
- 「单独用于返回投资日历的按钮」= 覆盖层工具栏里的 `#gapClose`（文案「返回日历 (Esc)」）。
- 为什么要真的加一对页卡、而不是只把按钮改个文案：**覆盖层是整屏的（z-index 60），会把顶栏整组 `.apptabs` 完全盖住**
  （已加断言用 `elementFromPoint` 证明这一点）。所以层内那对页卡不是冗余，是用户在层内唯一看得见的切换入口。
- 决定：**保留顶栏那组**（它是「从日历进入利润断层」的入口，不能删），层内新增一组**同构**的
  `.gap-tabs` / `.gap-tab`，两组的 `aria-selected` 由同一个 `setTab()` 一起同步。

### 改了什么（全部在 tools/build_preview.py 的 TPL 内）
- CSS：新增 `.gap-tabs/.gap-tab`（与 `.apptabs/.apptab` 完全同构：surface2 底 + `#3a3a3c` 选中）；
  两处 `@media` 把 `.gap-tab` 一并带上（900px 缩边距 / prefers-reduced-motion 关过渡）。
- 标记：`.gap-bar` 最左插入 `.gap-tabs[role=tablist]`，含 `#gapTabGap`（选中）/`#gapTabCal`；
  **删除 `#gapClose`**；`.gap-stage` 加 `id="gapStage"` 供 `aria-controls` 指。
- JS：加 `TAB_CAL_IN` / `TAB_GAP_IN` 两个引用；`setTab()` 同步两组；
  `openFrame()` 的焦点从 `#gapClose` 改为落在**当前页卡** `#gapTabGap`；
  层内两个页卡分别绑 `openFrame` / `closeFrame`（`openFrame` 本身幂等，所以点「利润断层」不会自我重载）。
- 移除按钮后原按钮上的 Esc 提示没丢：`#gapTabCal` 上加了 `title="切回市场日历（按 Esc 同样可以）"`。
- **日历本体依旧一字未改**：`git diff --numstat tools/build_preview.py` = `45 insertions, 8 deletions`，
  8 处删除全部落在 gap 模块（删按钮 1 行 + 被替换的 3 处缩进/注释行 + 两处 @media 行被加长）。

### 自检：jsdom 72 → **86 项**，真实浏览器 32 → **40 项**，全过
新增断言覆盖：页卡存在/对等/同属一个 tablist、`gapClose` 已消失、真实可见且并排、
顶栏此刻确实被盖住（`elementFromPoint` 命中 `#gapShell`）、层内选中态、点「利润断层」不重载且不重启超时、

### ⚠️ 负向测试逼出来的一个真问题（方法论，值得记）
「点『利润断层』不重启 30 秒超时」这条断言**最初永远不会失败**。
根因：4a 里为模拟「已加载完成」用了 `asCrossOrigin()`——它把 `contentWindow` 换成一个**读就抛错**的 getter。
一旦产品代码在点击时重设 `src`，**jsdom 内部的 iframe `loadFrame` 会去读 `contentWindow`**
（`HTMLFrameElement-impl.js: refreshAccessors`）→ 撞上 getter 抛错 → `setAttribute` 自己就炸了 →
`startLoad()` 里排在 `setAttribute` **后面**的 `setTimeout` 根本执行不到 → 定时器数不变 → 断言假通过。
修法：点页卡之前先 `restoreRealWindow()` 撤掉替身。
修完负向 B 从「2 项失败」变成「4 项失败」，那条定时器断言终于会打出 `timers 1 → 2`。
**教训：只要断言依赖的中间步骤可能先抛异常，就必须验证它真的会失败，否则是在给自己发安慰奖。**

### 🚨 发布环节踩的两个坑（都写进技能了）
1. **只推源码不会让线上产物更新。** 一开始以为「push 会触发云端重跑管线」（10-04 的误判），
   复核 `runs[].name` 后确认 `event=dynamic` 的 run 全是 GitHub 内置的 **`pages build and deployment`** ——
   只把当前 tree 重新发布到 Pages，**不重跑管线、不回推**。`daily.yml` 只在 21:00 cron 与 dispatch 上跑。
   实测：只推 `build_preview.py`、等 Pages 发布完，线上 `app.html` 里 `grep -c 'id="gapTabCal"'` **= 0**。
   → 正解是**显式 dispatch `daily.yml`**。
2. **dispatch 之后又 push → run 的第 8 步「提交更新」必挂。** 我在 dispatch（run #20）之后推了
   `webapp/index.html`，正好撞在 run 执行期间：**前 7 步全 success，只有「提交更新」failure**，
   仓库啥也没变。特征好认（只有第 8 步红）。→ **铁律：dispatch 到 run 结束之间一次都别推。**
3. 顺带确认：远端 `tools/data` 是今天 01:31 定时任务产出的（**比本地 10-04 的新**），
   所以**不能**把本地重建的产物推上去，否则会把当天数据覆盖回昨天。
